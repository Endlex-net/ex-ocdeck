# Proposal: task-permission-mode

## Why

目前 task 创建时不支持权限配置，底层 opencode 进程的权限行为完全取决于外部环境（用户全局/项目 opencode 配置），ocdeck 无法按任务控制，涉及高危工具时每次都需要人工 ask 逐条批准。对自托管编排场景，用户需要在创建任务时一次性决定该任务的授权策略：完全人工、完全自动、或 AI 辅助判定。

## What Changes

- 任务创建新增可选的权限模式配置，三档：**ask**（现状默认：不附加自动批准或 AI 判定，opencode 原生配置产生的权限请求由人工逐条处理，原生 allow/deny 行为不变）、**all-approve**（全部批准，无需人工逐条干预）、**ai-auto**（AI 自动识别每条权限请求是否可通过，AI 不可用时转人工）。
- 权限模式随任务创建持久化，创建后不可修改。
- 任务激活拉起 opencode 进程时，按任务持久化的权限模式施加对应的权限行为。
- ai-auto 模式下，权限请求由平台已配置的全局 LLM 自动判定通过或拒绝；LLM 未配置、调用失败或超时时，该请求保持待处理并转人工（退化为 ask 体验）。
- Web 新建任务表单增加权限模式选择，缺省为 ask（与现状行为一致，无破坏性变更）。
- ai-auto 的每条权限判定与回复结果写入独立审计日志文件，供用户查阅 AI 放行/拒绝了什么（含转人工与失败的记录）。
- ai-auto 判定上下文增强：判定输入从「任务名+工具名+patterns」扩展为平台语境（任务/项目/分支/目录）+ 按权限类别提取的请求详情（完整命令、文件目标、有界 diff 等），判定输出改为 XML 标签包裹格式（`<verdict>`），提高自动判定的信息质量与格式鲁棒性。

## Capabilities

### New Capabilities

- `task-permission-mode`: 任务级权限模式——创建时选定并持久化（ask / all-approve / ai-auto）、激活时按模式施加权限行为、ai-auto 的 AI 自动判定与人工兜底、ai-auto 判定与回复的独立审计日志。

### Modified Capabilities

（无。任务创建、进程编排、注意力管道的既有 requirement 保持为真，本变更以新增 capability 承载全部新行为。）

## Impact

- **任务创建链路**：创建请求 DTO、应用层选项、任务持久化（新增列与迁移）增加权限模式字段（纵向切片参照既有任务运行模式字段）。
- **任务激活 / 进程编排**：拉起 opencode 进程的参数按权限模式分化。
- **权限事件管道**：ai-auto 复用既有 opencode 权限事件捕获与 pending 对账能力，新增自动回复动作（含与人工回复的竞态处理）。
- **平台 AI 配置**：ai-auto 复用全局 LLM provider 配置与补全抽象，不新增配置体系。
- **运行日志**：ai-auto 判定与回复的审计记录追加写入数据目录 logs 下的独立文件，不影响既有日志结构。
- **权限事件观察层**：pending 权限请求的捕获范围增加请求详情（metadata），注意力对账与前端投影行为不变。
- **Web 前端**：新建任务表单与任务展示涉及权限模式字段。
- **兼容性**：既有任务与缺省创建行为不变（ask）；不涉及对存量数据的迁移改写（缺省值兜底）。
